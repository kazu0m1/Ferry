# Ferry v1.1.2 prototype 1 — Explorer向けD&D Move完了処理

## 現象
同一ドライブ内でFerryからWindows Explorerへfile/folderを通常D&Dすると、Explorer側にはitemが作成される一方、Ferry側sourceにも元itemが残り、見かけ上Copyになる場合がある。

## 原因仮説とWindows Shell仕様
Ferryは`FileDrop`を含むWPF `DataObject`を`DragDrop.DoDragDrop`へ渡しているが、v1.1.1まではdrop完了後のresultを使用していなかった。

Windows Shellのunoptimized MOVEでは、targetがdestinationへデータを転送したあとsourceへ元データの削除を依頼する。source側で削除してよい安全条件は次の両方がMOVEであること。

1. `DoDragDrop`の戻り値 = `DragDropEffects.Move`
2. 同じ`IDataObject`へtargetが書き戻す`Performed DropEffect` = MOVE

optimized MOVEではtarget自身がsourceを移動/削除するため、Ferryが追加削除してはならない。

## Prototype 1実装
- `DoDragDrop`の戻り値を保持する。
- `ClipboardHelper.WasUnoptimizedMovePerformed`で`Performed DropEffect`のDWORDを読む。
- 上記2条件がともにMOVEの場合だけ、まだ存在するsource pathを`ShellFileOperations.DeleteAfterExternalMove`で削除する。
- source pathがすでに存在しない場合はoptimized MOVEとして追加削除しない。
- final effectがCopy/Link/Noneの場合はsourceを一切削除しない。
- cleanup errorはmodal errorとして通知し、source viewをrefreshする。
- Debug LoggingがONの場合のみ、`finalEffect`と`performedMove`判定を記録する。

## 非変更範囲
- Ferry→Ferry internal D&DのMove/Copy判定とfile operation本体
- Explorer→Ferry D&D
- Paste result feedback (v1.1.1)
- Selection Engine / rubber-band / Selection Anchor / autoscroll
- Windows Shellのcollision UI

## Safety principle
`DoDragDrop`の戻り値だけではsource削除しない。`Performed DropEffect=MOVE`との二重条件を満たす場合だけunoptimized MOVEのsource cleanupを行う。
